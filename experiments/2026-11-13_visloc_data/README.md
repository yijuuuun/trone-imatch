# UAV-VisLoc 데이터 가공과 좌표 어긋남 확인

분담 1번(주희윤, [docs/07](../../docs/07_교수님_피드백_1113.md) 3장). UAV-VisLoc 전체를 새로 받아 `data/` 형식으로 만들고, 지난 실험(10 m 이내 15%)에서 의심된 좌표 어긋남을 확인했다.

**결론 한 줄**: 어긋남은 위성 지도가 아니라 드론 진행 방향을 따르는 10~16 m(GPS·촬영 시각 차이로 추정)지만, 비행마다 하나의 값으로 고쳐도 효과가 거의 없어(10 m 12.8% → 13.8%) **위치 보정 없이 GPS 그대로를 정답으로 쓰고 한계로 적는다.**

## 1. 데이터

[UAV-VisLoc](https://github.com/IntelliSensing/UAV-VisLoc) 비행 11개 중 10개(07은 자세 열이 없고 위성 지도가 띠라 뺌). 만드는 법은 [data/README.md](../../data/README.md).

| 폴더 | 내용 | 쓰는 실험 (분담 번호) |
| --- | --- | --- |
| `single_eval` | 한 장 1,738장 (비행마다 평가 줄에서 3장에 1장). set = `visloc_<비행>` | 원 Bearing-UAV(2), 다른 모델(5), 8/4방향(6) |
| `seq_eval` | 비행 구간 92개, 사진 1,112장. 구간마다 지도 4096 px(1,024 m), 순서대로 전부 | R1(3), R1 + R4(4), 거리별(7) |
| `single_calib` | 513장 (비행마다 앞쪽 20% 줄). 이 확인에만 썼다 | 평가에 쓰지 않음 |

Kaggle 비공개 데이터셋: `heeyunju/visloc-single-eval`, `heeyunju/visloc-seq-eval` (팀원은 공동작업자로 추가). 커널 실행 코드가 `samples.csv`를 하나만 찾기 때문에 둘을 따로 올렸다.

```bash
python scripts/kaggle/build_kernel.py --user <아이디> --dataset heeyunju/visloc-single-eval --slug <이름> --args "--matchers loma --angles 8"
```

### 가공 기준

| 항목 | 기준 | 근거 |
| --- | --- | --- |
| 블록 | 고정 격자(256 px 간격)에서 정답을 담은 512 px 블록. GPS 중심으로 자르지 않음 | 지난 변환은 정답이 모두 블록 정중앙(`x_norm = 0`)이라 "가운데" 답이 이긴다. 지금은 \|x_norm\| 평균 0.50 |
| 위성 지도 | 0.25 m/px, 북쪽 위로 다시 샘플링. 동서·남북 축척을 따로 맞춤. 09는 tif 4장을 이어 붙임 | 원 픽셀이 땅에서 동서 0.23~0.27, 남북 0.30 m. SIFT로 맞춰 보면 따로 맞춘 뒤 비율 1.01~1.02 |
| 드론 영상 | 가운데 64 m를 256 px로 | 3D 데이터와 같은 0.25 m/px |
| 드론 축척 | 비행마다 연속 사진 쌍(20쌍)의 SIFT 이동량 ÷ GPS 거리 | EXIF가 없고 height가 해발 고도. 03 0.1125(지난 실험 0.1128), 11 0.1820(위성 SIFT 0.1817) |
| heading | 정답에만 씀, 입력 아님. theta = -Phi1 | Phi2는 비행에 따라 Phi1과 21°까지 다름 |
| 빼는 것 | 07, 고도 중앙값 ±10 m 밖(상승 구간), 블록이 지도에 다 안 들어가는 것 | 정답을 만들 수 없음 |
| 표시만 | `tilted`(자세 5° 초과, 135장), `turning`(회전 중, 83장) | 교수님 피드백 11(챌린징한 상황). 빼지 않음 |
| 나눔 | 비행 줄 단위. 앞쪽 20% 줄 = calib, 나머지 = eval | 연속 사진이 약 70% 겹쳐 사진 단위로 나누면 섞인다 |

비행별 축척·지도 정보는 [flights.csv](flights.csv).

## 2. 좌표 어긋남 확인

`single_calib` 513장을 LoMa 8방향으로 돌렸다(Kaggle T4, 커널 `heeyunju/visloc-calib-loma8`).

```bash
python scripts/run.py --data data/visloc/single_calib --out outputs/visloc_calib --matchers loma --angles 8
python scripts/visloc_calib.py outputs/visloc_calib/loma_s1.csv --data data/visloc/single_calib --out offset_estimates.csv
python experiments/2026-11-13_visloc_data/cv_offset.py data/visloc/single_calib/samples.csv experiments/2026-11-13_visloc_data/loma_calib_s1.csv
```

### 2.2 어긋남은 지도가 아니라 드론 진행 방향을 따른다

inlier ≥ 15이고 오차 60 m 안인 샘플로 (추정 − 정답)을 봤다.

| 비행 | 진행 방향 앞쪽 어긋남 (갈 때 / 올 때) |
| --- | --- |
| 03 | +9.8 / +10.2 m |
| 04 | +15.4 / +16.1 m |
| 05 | +13.4 / +13.4 m |
| 09 | +16.9 / +7.3 m |
| 11 | +11.8 / +1.6 m |
| 01 | −12.9 / +13.3 m |

- 03·04·05는 갈 때와 올 때가 같다. 지도 좌표가 틀렸다면 지도 위에서 같은 방향이어야 하는데, 드론 기준으로 같은 방향이다 → GPS 기록 시각과 촬영 시각 차이로 추정 (03은 초속 약 16 m라 약 0.6초). 원인은 확정하지 않았다.
- 01·09·11은 방향마다 다르다.
- 비행별 보정값 전체는 [offset_estimates.csv](offset_estimates.csv).

### 2.3 비행마다 한 값으로 고치면 효과가 거의 없다

보정용 줄을 홀짝으로 나눠, 한쪽으로 보정값을 정하고 다른 쪽에서 쟀다(2겹, 391장. 05·06은 보정 샘플이 적어 3장씩만 남음, 08·10은 제외).

| 보정 방식 | 10 m | 20 m |
| --- | --- | --- |
| 보정 없음 | 12.8% | 35.5% |
| 드론 기준 (앞뒤·좌우 한 값) | 13.8% | 36.8% |
| 지도 기준 (동서·남북 한 값) | 6.6% | 23.3% |

- 03(26 → 32%)과 04(12 → 17%)는 좋아지고, 01(20 m 29 → 11%)과 11(10 m 16 → 8%)은 나빠진다.
- 지도 기준 보정은 오히려 나빠진다 → 위성 지도 좌표 문제가 아니다.

## 3. 결정

- **위치 보정 없이 공유한다** (`data/visloc`, 정답 = GPS). 어긋남은 2.2·2.3 숫자를 근거로 한계로 적는다. docs/07 5장의 "원인을 더 팔지, 한계로 명시할지"에 대한 답.
- 10 m 기준은 라벨 오차(약 10~16 m)에 민감하므로 **20 m, 32 m도 같이 보고**하는 것을 권한다.
- heading 보정(비행별 1~5°, `offset_estimates.csv`의 head_off)은 이미지가 바뀌지 않으므로, 필요하면 나중에 정답만 바꿔 다시 채점하면 된다(다시 돌릴 필요 없음).

## 4. 한계

- GPS·촬영 시각 정렬, 위성 지도 촬영 시기는 확인하지 않았다.
- 드론 축척은 카메라 보정값이 아니라 연속 사진으로 잰 값이다(비행별 MAD 0.004~0.019 m/px). 05는 LoMa 추정 축척 중앙값이 1.11, 04는 1.06으로 1에서 조금 멀다.
- 드론 사진(약 440 × 300 m)의 가운데 64 m만 쓴다. 3D 데이터와 같은 형식으로 비교하기 위해서다.
- `seq_eval` 구간은 지도 한 장(1,024 m)에 들어가야 해서 길이가 600~1,000 m(중앙값 948 m)다. 사진 간격이 60~130 m라 시뮬레이터(15 m)와 다르다. R1·R4를 돌리려면 기록된 경로를 따라가는 재생 모드가 필요하다(지금 `run_nav.py`는 닫힌 루프 시뮬레이터).
