# UAV-VisLoc 항법: 확정 v1(4방향 + 멈추기 15)로 R1, R1 + R4 (분담 3·4)

[#36](../2026-11-14_visloc_nav/README.md)은 8방향으로 돌렸다. 개발용 데이터 두 곳(학습 도시 [2026-11-16_heading_train](../2026-11-16_heading_train/README.md), VisLoc `single_calib` [#40](../2026-11-16_heading_dirs_visloc_calib/README.md))에서 4방향이 확정된 뒤, 시험용 `seq_eval`을 **확정 v1로** 다시 돌린 결과다. 이 문서가 보고서에 들어갈 최종 숫자다.

**결론 한 줄**: v1(R1 + R4)은 92구간 중 72구간(78.3%)이 마지막 40 m 이내로, 원 모델 Bearing-UAV(41구간, [#42](../2026-11-16_bearing_visloc_colab/README.md))와 추측 항법(56구간)보다 확실히 많다(36 vs 5, p = 8e-07 / 23 vs 7, p = 0.005). 걸음당 매칭 시간은 3.57초. R4는 R1보다 3구간 더 살렸지만 유의하지 않다(p = 0.25).

## 1. 설정

- 데이터: `heeyunju/visloc-seq-eval` 92구간, 1,020걸음(출발 제외). 구간 600~1,000 m, 사진 간격 60~130 m.
- 매처 LoMa, 4방향 + 멈추기(inlier ≥ 15). 나머지는 #36과 같음: 이동 오차 vio(치우침 3°, 걸음 방향 2°, 축척 5%), seed 2026.
- **출발 위치는 GPS로 준다**(첫 사진은 매칭하지 않음). 원 모델 항법 #42와 같은 조건이다. #36과 이 실험의 첫 실행은 첫 사진도 매칭해서 그 답으로 출발했다(R0는 92구간 중 31구간이 40 m 넘게 틀린 채 출발). `imatch/replay.py`를 고쳤다.
- **걸음당 시간은 걸음마다 기록한 매칭 시간(재매칭 포함)의 평균**이다. 예전 표(#36)는 전체 경과 시간 ÷ 걸음 수였는데, variant끼리 매칭 캐시를 같이 써서 뒤에 돈 R1·R4가 짧게 나왔다. `scripts/run_visloc_nav.py`를 고쳤다.
- Kaggle T4, 1시간 21분.

```
python scripts/kaggle/build_kernel.py --user yijuniverse --dataset heeyunju/visloc-seq-eval --slug visloc-nav-v1-4dir --script run_visloc_nav --args "--matcher loma --angles 4 --stop-inl 15 --variants dr,r0,r1,r4g0n5w20 --odo vio --seed 2026"
```

| variant | 뜻 |
| --- | --- |
| dr | 매칭 없이 추측 항법만 |
| r0 | 매칭 결과 항상 믿음 (오류 처리 없음, 원 모델과 같은 조건) |
| r1 | inlier < 15면 "모름" → 추측 위치 (v1 예방) |
| r4g0n5w20 | r1 + "모름"이면 그 걸음에서 바로 십자 5블록 재매칭, 5걸음 연속 "모름"이면 3×3 9블록(inlier ≥ 20) (v1 복구) |

| 출발부터 | dr | Bearing-UAV | LoMa r0 | r1 | r1 + r4 |

추측 항법은 거리에 따라 오차가 계속 커지고(8 → 27 m), R1·R4는 거의 일정하다(15 → 24 m). 짧은 구간에서는 추측 항법이 낫지만 600 m를 넘으면 뒤집힌다. 추측 항법의 이동량은 GPS 차이에서 만들었고 GPS 라벨 어긋남(10~16 m)은 매칭에만 불리하게 작용하므로, 실제 비행에서는 추측 항법이 이보다 불리하다.

## 3. 8방향(#36)과 비교

#36은 첫 사진도 매칭한 조건이라 완전히 같은 조건은 아니다(R1·R4는 영향 작음: 첫 사진 오차 중앙값 2~6 m).

| | 8방향 (#36) | 4방향 (이번) | 한쪽만 40 m 이내 (4 / 8) | p |
| --- | --- | --- | --- | --- |
| r1 마지막 40 m 이내 | 70.7% | 75.0% | 4 / 0 | 0.13 |
| r1 + r4 | 76.1% | 78.3% | 3 / 1 | 0.63 |
| r1 걸음당 s | 1.39 | 0.74 | | |
| r1 + r4 걸음당 s | 7.29 | 3.57 | | |

4방향이 정확도 손해 없이 시간을 약 절반으로 줄였다. #36의 시간(0.91, 5.60초)은 위의 캐시 문제로 짧게 적힌 값이고, 걸음별 기록으로 다시 계산하면 1.39, 7.29초다.

## 4. R4가 얼마나 자주, 얼마나 도움이 되나 (1,020걸음)

| | 걸음 | 비율 | 구간 |
| --- | --- | --- | --- |
| 매칭 믿음 (inlier ≥ 15) | 519 | 51% | |
| "모름" → 재매칭 시도 (십자 또는 3×3) | 501 | 49% | |
| └ 3×3까지 간 걸음 (5걸음 연속 "모름") | 161 | 16% | 35 / 92 |
| 재매칭으로 위치를 되찾음 | 25 | 2.5% | 23 / 92 |
| └ 그중 3×3로 되찾음 | 3 | 0.3% | |

- 3×3 걸음은 걸음당 9.9초(나머지 2.4초)로 전체 매칭 시간의 44%를 쓴다.
- 재매칭이 위치를 되찾는 일은 드물지만(2.5%), 구간 4분의 1(23/92)에서 한 번 이상 일어난다. 마지막 40 m 이내는 R1보다 3구간 늘었다.
- 시간을 줄이려면 3×3 횟수를 줄이는 게 가장 효과가 크다(예: 3×3 뒤 다시 5걸음 기다리기).

## 5. 한계

- 시험용 데이터를 보고 바꾼 설정은 없다. 4방향과 R4 포함은 이 실행 전에 개발용 데이터와 팀 결정으로 정했다. 출발 위치·시간 계산 수정은 평가 규칙의 버그 수정이고 설정 변경이 아니다.
- 92구간이라 R4 효과(3구간)는 통계적으로 검출되지 않는다.
- GPS 라벨 어긋남(10~16 m)을 보정하지 않았다. 10 m 기준은 낮게 나온다.
- 한 번의 실행, 한 가지 이동 오차 seed. 원 모델은 Colab T4, 우리는 Kaggle T4.
